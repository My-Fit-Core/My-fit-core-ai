## 1. 한 줄 목표

내 옷장 옷을 사진 한 장으로 등록(검출·누끼·태깅)하고, 날씨 × 추구미 기반 코디 3종과 슬롯 교체 후보를 추천하는 AI 서버를 남은 3주(11/23 기준, 마감 약 12/14 `[가정]`) 안에 MVP로 완성한다.

기한이 짧아 추구미는 원안 15종이 아니라 **기본 5개를 제대로 구현하는 것**에 집중한다. 나머지는 2차 로드맵이다(팀 합의).

## 2. 구조와 기술 스택

```
[앱] → [Supabase Storage] → [백엔드(Supabase+Vercel)] --분석 요청(비동기)--> [AI 서버(이 레포)] --콜백--> [백엔드]
                                                      --추천 요청(동기)--> [AI 서버]
```

| 영역 | 확정 | 미정 |
| --- | --- | --- |
| 언어·서빙 | Python 3.11, FastAPI + Uvicorn, Docker 이미지 하나, 패키지 버전 고정(현재 버전으로 고정 완료, 방식은 개발 시작 즈음 협의) | 서빙 플랫폼 (Modal / RunPod / 직접) |
| 검출 | YOLO (DeepFashion2, `deepfashion2_yolov8s-seg.pt`), 부위 판정도 YOLO 클래스 | 신발·가방·액세서리 검출 방법 (아래 §9) |
| 분할·누끼 | YOLO 자체 마스크 + 구멍 메우기 | SAM 2.1 tiny 추가 여부 (시간 남을 때) |
| 태깅 | FashionCLIP zero-shot. 입력은 마스크 밖을 흰색으로 지우고 박스로 자른 사진. 색상은 마스크 픽셀 k-means | 소분류 목록 |
| 추구미 점수 | 옷 한 벌 `prompts.item`(보정 없음), 코디 사진 `prompts.outfit`(고정 prior 보정) | - |
| 추천 | 규칙 기반 점수 함수 `recommend/`, **AI 서버에서 실행, 동기 응답**(10/12 회의 합의) | - |
| LLM 코멘트(P1) | 경량 LLM API | 모델 |
| 벡터 | 백엔드 DB에서 임베딩 별도 관리 `[확인]` | 임베딩을 요청·응답에 담는 방식 |

- 코드 규칙: ruff, 타입 힌트, pydantic 요청/응답, 모델은 서버 시작 시 1회 로드, 비밀값은 환경변수.
- 라이선스: DeepFashion2 가중치는 비상업용. 공개 서비스 전에 교체 또는 허용 여부 확인 `[미정]`.

## 3. MVP 범위

- F-304 코디 슬롯 교체 후보 랭킹

포함 (P1, 오픈 베타 전. 시간 부족하면 여기서 자른다)
- F-303 LLM 스타일리스트 코멘트
- F-402 내 옷장으로 따라입기 (유사도 매칭률)

제외 (2차 로드맵)

- 원안 15종 추구미와 마이크로 트렌드(Y2K, 모리걸 등). 3주 기한 때문에 기본 5개만 구현하고, 나머지는 그 위에 추가한다(2계층 구조는 합의, 목록은 `configs/aesthetics.yaml` 설정으로 받는 구조 유지).
- SAM 추가 검토(#41 비교)는 시간이 남을 때만. 기본은 YOLO 마스크.
- 남성 타겟 구현(아키텍처만 확장 가능하게, 구현은 2차).
- 퍼스널컬러·체형 분석(하지 않기로 결정).
- 옷 종류 영향 제거 보정, linear probe(#34), 색 기반 추구미 보정(검증 실패, #50).

| 분석 방식 | **비동기, 결과는 콜백**으로 백엔드에 전달 `[확인]`(회의 답변이 콜백 결과 형식으로 적혀 있음) | 안건 4 |

| 작업 상태 | AI 서버가 쓰는 4개(대기·진행중·완료·실패) 그대로. 백엔드는 대기·진행·취소를 따로 관리 | 안건 7 답변 |
| 에러 형식 | `{"code": "...", "message": "...", "client_item_key": "옷 키 또는 null"}`(사진 전체 오류는 null). 재시도 가능 여부는 백엔드가 판단 | 안건 8 답변 `[확인]` |

## 7. 예외·실패 처리 (구현 시 반드시 포함)

AI 서버가 반환할 에러 코드는 백엔드 임시안(§4)을 기준으로 한다 `[확인]`.

| 상황 | 처리 |
| --- | --- |
| 검출 0벌 | `NO_GARMENT_DETECTED`, 결과 `failed` |
| 7벌 이상 | 상위 신뢰도 6벌까지 반환(누끼 URL 개수보다 많으면 URL 개수까지) |
| 일부 옷만 실패(누끼 업로드·태깅) | 성공분은 `items`, 실패분은 `errors`에 `client_item_key`와 함께, 결과 `partial_failed` |
| 사진 다운로드·누끼 업로드 실패 | `STORAGE_UNAVAILABLE` |
| 이미지 규격 위반(형식·용량·손상) | 원인 특정이 어려우면 `ANALYSIS_FAILED`. 전용 코드가 필요하면 백엔드에 요청 `[확인]` |
| 짧은 변 <512px | 분석은 진행하고 경고 정보 포함 `[제안]` |
| 모델 로드 실패 | `MODEL_UNAVAILABLE`, `/health`에 반영 |
| 처리 시간 초과 | `WORKER_TIMEOUT` |
| 예상 못한 오류 | `INTERNAL_ERROR` 또는 `ANALYSIS_FAILED`(통합 예외) |
| 카테고리 확신 낮음 | 상위 3개 후보를 모두 반환(사용자 수정) |
| 옷장이 부족해 코디 3종을 못 만듦(예: 하의 없음) | 가능한 만큼 반환하고 사유 포함 |
| 날씨 필드 결측(체감온도·미세먼지 등 선택 값) | 있는 값만으로 계산하고 결과에 표시 |
| 옷 종류 쏠림으로 한 스타일 코디만 추천 | 세트 간 다양성 규칙으로 완화 |

## 8. 팀·백엔드에 남은 확인 `[미정]`

AI 파트가 답해야 하는 것
- 사진 1장당 최대 옷 수(`max_det`): **6벌**로 답 예정(승인 조건과 동일). 백엔드가 누끼 URL 개수를 이 값으로 제한.
- 6종 밖 라벨(원피스 등)을 `category`에 그대로 보내도 되는지: 원피스는 1020 여성 타겟에 중요하므로 대분류에 `dress` 추가 요청을 제안.
- 소분류 목록: AI가 정해서 전달. `configs/categories.yaml`에 `category-taxonomy.md` 안 A 초안이 있다(T14에서 `aesthetics.yaml`의 옛 블록을 옮김, 확정 아님).
- 입력 규격 최종값: 긴 변 2048px 상한을 유지할지(20MB로 올리면 큰 사진이 올 수 있음), WebP 디코딩 지원.

백엔드에 확인할 것
- `client_item_key` 부여 방식: 누끼 업로드 URL과 1:1로 묶이는 키로 보이는데, 검출된 옷을 어떤 순서로 URL에 배정하는지.
- AI 서버 인증 방식(공유 비밀키 헤더 제안에 답이 없음), 콜백 URL과 콜백 인증.
- 임베딩 전달 방식("임베딩 DB 따로 분류"의 의미): 분석 응답에 포함할지, 추천 요청에 옷마다 담을지.
- 에러 코드 7종 동의 및 이미지 규격 위반 전용 코드 필요 여부.

그 밖의 미정
- 서빙 플랫폼·비용, 테스트 사진 공유 저장소 위치
- 신발·가방·액세서리를 MVP에서 어떻게 다룰지(§9)

## 9. 문서 불일치·위험 (보고)

- **검출 범위 불일치**: 백엔드 대분류 6종에는 `shoes`, `bag`, `accessory`가 있는데, 현재 검출기(DeepFashion2 YOLO)와 K-Fashion 라벨은 상의·하의·아우터·원피스 중심이다. PoC도 "신발과 잡화는 라벨이 없어 평가하지 않는다"(`261108-0305-01-detection-segmentation-poc.md`), `configs/aesthetics.yaml`도 "신발·모자는 검출 대상이 아니다"라고 적혀 있다. 3주 안에 MVP 검출을 상의·하의·아우터·원피스로 한정할지 결정이 필요하다 `[미정]`. (DeepFashion2 클래스 13종은 실제 가중치에서 확인함, 11/23: 상의·아우터·하의·원피스 계열만 있다.)
